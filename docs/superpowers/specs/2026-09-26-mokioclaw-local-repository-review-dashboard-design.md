# MokioClaw 本地仓库提交审查工作台设计

> 日期：2026-09-26（Asia/Shanghai）
> 状态：用户已确认书面设计（2026-09-26）；本文件本身不授权代码实施或真实 Agent 运行
> 基线：main / 94e3c33bc485a9e54c6f9cf6d6de16d8ee55c80d
> 阶段定位：先交付本地浏览器中的仓库列表、提交历史与可解释的改动审查优先级；私有 GitHub 接入和 Agent 修复为后续独立增量

## 1. 目的与用户意图

MokioClaw 的长期目标仍是面向真实仓库的 Issue → Patch → Test → Review 维护 Agent。上一阶段完成了可审计的 Rich、Click 固定快照评测，但项目尚缺一个直观的产品入口。用户希望最终演示通过 GitHub 账户展示仓库列表、提交历史及对应风险评估；为了尽快推进，先实现本地仓库核心，并选择本地浏览器页面。第一版的“风险”已明确为**改动审查优先级**，不是漏洞检测、故障概率或 Agent 修复成功率。

本阶段的目标是：用户显式选择若干本地 Git 仓库，打开本机浏览器，在左侧选仓库、在中间浏览提交、在右侧查看某条提交的审查优先级、具体依据和信息缺口。展示过程不修改仓库，不调用模型，不运行仓库代码，也不产生新的 Agent Benchmark 成绩。

### 1.1 面向的人

- 作品演示观看者：在数分钟内理解 MokioClaw 处理真实仓库的入口和可解释的审查信息。
- 仓库维护者：快速找到更值得人工先看的提交，并能追溯优先级的依据。
- 后续开发者：在同一数据契约上增加私有 GitHub 来源和人工触发的 Agent 修复，不重写风险展示层。

### 1.2 成功标准

1. 两个或更多由用户显式指定的本地仓库能够同时出现在仓库列表，切换仓库不会串用提交数据。
2. 提交历史可以分页；点击提交后，文件统计、优先级、命中规则和不确定性都绑定到同一个完整 SHA。
3. 对相同提交对象与同一规则版本，评估结果与绝对路径、时区、locale 和页面刷新无关。
4. 所有读取都保持仓库工作树、Git 引用、index、忽略文件和既有实验产物不变。
5. 没有模型调用、远端写操作、自动测试执行或隐式仓库扫描。
6. 用户可以从界面辨认“优先审查”与“已证实缺陷”的区别。

## 2. 现状与证据边界

当前代码有 Typer CLI、Textual TUI、Agent 会话、审批、checkpoint、trace，以及独立的 Eval Runner、Docker 工具平面、补丁捕获和报告。没有浏览器服务、通用本地仓库目录、提交级审查优先级计算或 GitHub 账户授权模块。Eval 的 Docker 隔离仅对其实际执行路径成立，不能描述为普通 CLI/TUI 的通用沙箱。

Rich–Click 最终比较位于 evals/reports/cross-repo-rich-click-20260926-01/。两个 Q1 维度是 divergent，Q2 是 inconclusive，顶层 direction_comparison 是 inconclusive，strict_audit_status 是 legacy-audit-limited。新工作台不重算、不覆盖、也不把这些实验结论变成提交风险标签。产品代码修改后，新的框架树与冻结 Click 身份不同；旧批次仍只对应其冻结版本。

## 3. 路线选择

### 3.1 已选路线

第一版使用**本地 Git 仓库 + 本地浏览器页面 + 只读规则评估**。这与用户确认的速度优先选择一致，也让提交分析在没有 GitHub 授权、网络和 provider 的情况下完成。界面保留与未来 GitHub 来源兼容的仓库、提交、评估数据形状，但不预建通用插件框架。

### 3.2 实现形态

采用一个只监听本机回环地址的小型 Python Web 服务，同进程提供静态页面和只读 JSON 接口。建议使用 FastAPI 与 Uvicorn，前端采用原生 HTML/CSS/JavaScript，不引入 Node 构建链、数据库、后台队列或 SSE。选择成熟路由框架是为了清晰处理参数、错误和测试；Web 服务仍只作为本地产品入口，不对外部署。Python 标准库 http.server 只提供基础安全检查，故不作为将来可延伸到私有仓库的服务基础。

### 3.3 被推迟的路线

- 不先把既有 Textual TUI 改成仓库工作台；TUI 保留 Agent 会话用途。
- 不做静态截图假数据作为主要产品入口；演示必须读取真实 Git 对象。
- 不在第一版做 GitHub 登录、私有仓库授权、webhook、云部署或 PR 回写。
- 不把 Agent 修复按钮伪装为可用功能；接入时需要单独的执行、安全和用户授权设计。

## 4. 版本范围

### 4.1 第一版包含

- 启动命令显式接收一个或多个本地仓库路径；未给路径时可以选择当前工作目录，但只有它本身是可读 Git 工作树时才启动。
- 页面左栏列出本次启动登记的仓库；不扫描磁盘寻找仓库。
- 页面展示当前分支或 detached HEAD、HEAD SHA、工作树是否有未提交变更。未提交变更只作为状态提示，不混入历史提交的优先级。
- 默认展示当前 HEAD 可达的提交历史，按 Git 的提交顺序分页，每页上限 50 条。
- 提交详情展示完整 SHA、简短标题、提交时间、父提交数量、文件变更类型、增加/删除行数及统计不可用的原因。
- 规则引擎生成 high、medium、low 或 manual_review 四种审查优先级，逐条列出命中依据、信息缺口和规则版本。
- 错误、空列表、正在加载、仓库变更和超时都有明确页面状态。

### 4.2 第一版不包含

- 读取仓库源码正文或完整 diff 并发送给模型；不读取 .env 的秘密值。
- 在浏览器中新增或删除仓库登记；第一版通过启动参数配置本次仓库列表。
- 跨所有分支、全部远端引用或整个用户磁盘的自动索引。
- 对每条提交运行测试、lint、漏洞扫描或 Agent。
- 根据提交作者、姓名、邮箱、提交消息措辞判断风险。
- 数值化缺陷概率、漏洞严重度、跨仓库质量排行或自动 PR。

## 5. 用户流程与页面信息架构

### 5.1 进入与选择

用户以新命令启动工作台，并显式提供仓库路径。命令只接受本机目录，不接受 URL；启动前逐项核对路径存在、可读取、解析后的路径与 Git 顶层目录关系清晰，并给出失败仓库的具体原因。成功后服务绑定 127.0.0.1 的可用端口并打开浏览器；终端同时显示地址和停止方式。启动不修改被展示的仓库。

页面为三栏：

| 左栏：仓库 | 中栏：提交 | 右栏：审查 |
|---|---|---|
| 显示名称、分支、工作树状态；支持切换 | 标题、短 SHA、提交时间、分页 | 完整 SHA、变更统计、文件列表、优先级依据、局限 |

页面至少适配常见桌面宽度；窄窗口可将详情移到列表下方。颜色不能是优先级的唯一表达方式，所有状态有文字标签。仓库、提交和详情选中状态必须明显；刷新后可以用页面 URL 中的非敏感仓库 ID 和 SHA 恢复选中项。

### 5.2 观察与解释

点击提交先展示其身份，再展示评估。文件名和标题按普通文本渲染，不作为 HTML 注入。界面总是标注“改动审查优先级（启发式）”；每条原因指出哪个可观测信号触发，缺少测试/CI 证据时明确写“未取得”，不写“测试失败”。高优先级意味着建议先人工看，不意味着已发现漏洞。

仓库或提交切换时立即清空旧详情并显示加载态。前端取消或忽略先前请求的迟到响应，并核对返回的仓库 ID 与完整 SHA，避免把 A 仓库的评估显示在 B 仓库的选中项旁。键盘可到达仓库、提交、翻页和刷新控件，焦点状态可见。

### 5.3 后续行动边界

第一版详情页可以解释未来可能存在“创建维护任务”的位置，但不能出现会让人误以为已经可执行的按钮。下一增量若接入 Agent，必须由用户主动触发，在独立工作空间形成补丁与测试报告，且不得自动修改来源仓库或远端。

## 6. 组件与数据流

1. **CLI 启动器**：校验显式路径，建立本次进程内仓库目录，启动本地服务并打开浏览器。
2. **RepositoryCatalog**：为每个已登记仓库分配进程内不透明 ID，保存规范化顶层路径；不接受浏览器传来的任意磁盘路径。
3. **LocalGitReader**：用参数数组调用 Git，只读取得 HEAD、工作树状态、分页提交和单条提交的元数据/变更统计。不得通过 shell 拼接命令。
4. **CommitNormalizer**：将 Git 输出规范化为与来源无关的 RepositorySummary、CommitSummary、CommitDetail；内部保留完整 SHA 和规则输入，不把本机绝对路径作为评估输入。
5. **ReviewPriorityV1**：纯函数，输入规范化提交统计，输出优先级、按稳定顺序排列的规则命中、信息缺口和规则版本。
6. **只读 API 与页面**：只接受已登记仓库 ID 和合法 SHA；同源提供页面资源与 JSON。页面不直接访问文件系统。

未来 GitHub 来源只需产出相同的规范化提交输入；不要求 LocalGitReader 为远端认证或 PR 写回预留抽象方法。这样保留数据契约，避免现在建一套无用的通用连接器框架。

## 7. Git 读取契约

- 只使用 Git 的读取操作，并对可能刷新 index 的查询使用 --no-optional-locks。所有 subprocess 采用参数数组、固定可执行文件、固定子命令、明确超时和输出上限，不通过 shell 执行仓库内容。调用时禁用可由仓库配置触发的外部 diff、textconv 和 fsmonitor 程序；不得信任仓库自带配置可以执行的命令。
- 仓库路径必须先 resolve，并以 Git 返回的顶层目录为登记身份；bare 仓库、不可访问目录和非 Git 目录在第一版拒绝。
- 提交列表固定在打开仓库时取得的 HEAD SHA 上分页。若 HEAD 后续移动，页面显示“仓库已更新，刷新列表”，避免不同分页混合两个历史视图。
- 提交详情必须使用完整 SHA；不接受分支名、修订表达式或用户拼出的 Git 选项作为详情 ID。根据该仓库的对象格式验证完整 SHA（SHA-1 为 40 位，SHA-256 为 64 位），再确认它在当前列表的锚 SHA 历史中可达。
- 文件名使用 Git 的零字节分隔格式解析，避免空格、换行或特殊字符造成错位；文件状态与 numstat 合并为一条规范化记录，重命名同时保留旧路径和新路径；前端将路径作为文本渲染。
- 只取得提交标题、时间、父 SHA、文件路径、变更类型与 numstat；不读取完整 diff、blob 内容或 .env 内容。Git 外部 diff/textconv 功能保持关闭。
- 根提交按空树比较。合并提交在第一版显示父提交数和“需人工审查”；不从任意一个父提交的差异推断完整合并风险。
- 对二进制、浅克隆导致的统计缺失及不支持的统计格式，保留明确的不可判定原因并输出 manual_review，不补零。提交对象不存在返回 404；Git 超时或输出截断返回明确错误，不产出基于半截数据的评估。
- 工作树 dirty 标志独立于某个已提交 SHA 的评估，不把本地未提交文件计入该提交。

## 8. 改动审查优先级 V1

### 8.1 定义

输出只允许 high、medium、low、manual_review。前三者是**人工审查顺序建议**，不是正确性、安全性或生产事故概率。manual_review 表示输入不完整或该提交类型超出 V1 的机械规则，不比 high 更安全。每个输出都包含规则版本、提交完整 SHA、可复算的信号、命中理由及信息缺口。不得给出 0–100 风险分数。

### 8.2 信号

规则只读取提交统计，不读取提交正文、代码正文或作者身份：

| 信号 | 机械来源 | 对用户的表述 |
|---|---|---|
| 文件数与总增加/删除行数 | Git 提交统计 | 改动范围较广 / 改动量较大 |
| 删除或重命名 | Git 文件状态 | 需要核对调用方或引用 |
| 敏感维护面路径 | 路径段与固定文件名规则 | 涉及依赖、构建、权限或 CI 等需优先审查的区域 |
| 测试文件是否同次改动 | 路径类别 | 仅作背景信息，不推断测试通过或失败 |
| 合并、二进制、统计缺失 | 父数或 numstat 状态 | 本规则无法可靠判断，建议人工审查 |

敏感维护面仅以路径作启发式识别。路径统一为斜杠分隔并做大小写折叠；路径段必须**完整等于** auth、authorization、permission、permissions、security 或 approval 之一，或文件名为 pyproject.toml、setup.py、uv.lock、poetry.lock、Pipfile.lock、package.json、package-lock.json、pnpm-lock.yaml、yarn.lock、Dockerfile，或匹配 requirements*.txt、Dockerfile*、.github/workflows/ 下的文件。命中只说明“改到了这类位置”，不能据此宣称发现漏洞。规则文件与实现共同版本化；未来变更阈值或路径集合必须升级版本并更新黄金测试。

### 8.3 固定判定顺序

1. 多父合并提交、二进制统计不可得或任何评估必需字段不完整：manual_review。不存在的提交、Git 超时或输出截断走接口错误，不进入此规则。
2. 命中敏感维护面路径，或变更文件数 ≥ 10，或总增加与删除行数 ≥ 500：high。
3. 否则，变更文件数 ≥ 4，或总增加与删除行数 ≥ 120，或存在文件删除/重命名：medium。
4. 其余完整普通提交：low。

阈值是第一版的**审查队列启发式**，不是从 Rich/Click Agent 成绩拟合出的预测模型。高优先级不替代测试和人工代码审查。测试文件未变、CI 数据缺失、作者身份和提交消息都不改变优先级；它们可作为信息缺口或背景字段出现。用户不能通过调整规则来“改善”某条演示提交的结果。

### 8.4 解释与确定性

理由使用固定模板与稳定排序；不让模型自由生成风险叙述。纯函数不读取时钟、网络、本机绝对路径或工作树。对同一 SHA、同一规范化输入和同一规则版本，JSON 字段、理由顺序与优先级相同。界面应允许用户看到原始变更统计与触发条件，而不是只看到标签。

## 9. 本地 API 与响应契约

API 仅向同源页面提供读取：

| 方法与路径 | 响应 | 边界 |
|---|---|---|
| GET /api/repositories | 本次登记的仓库摘要 | 不返回凭据；绝对路径可在本机 UI 显示，但不进入风险身份 |
| GET /api/repositories/{id}/commits?cursor=... | 最多 50 条提交、当前 HEAD 锚、下一页游标 | 游标绑定仓库 ID 与锚 SHA；限制长度并验证内容；无效游标返回明确错误 |
| GET /api/repositories/{id}/commits/{sha}?anchor=... | 单条提交详情与 V1 评估 | 完整 SHA 与列表锚都校验；提交必须在该锚历史中可达；不存在返回 404 |
| GET /health | 本地服务可用性 | 不泄漏仓库详情 |

接口不提供任意路径读取、命令执行、远端 URL 获取或仓库写入。错误结构固定包含 code、message、retryable；不返回 Python traceback、Git 配置内容或原始 stdout/stderr。前端根据 code 展示用户可操作的提示。静态资源由同源服务提供，不使用第三方 CDN。

## 10. 安全、隐私与权限

- 服务只监听 127.0.0.1，使用可用端口；拒绝不符合本机地址的 Host，默认不开放 CORS，不对局域网或公网暴露。
- 页面采用限制性内容安全策略；所有 Git 字符串仅以文本节点渲染。API 只能访问启动时已登记的仓库，不接受客户端提供的文件系统路径。
- 不存储 GitHub token、不读取 .env 秘密值、不把密钥、Authorization、完整 endpoint/query、prompt/response、headers 或 payload 写入产物。
- 不把仓库内容发送给 provider。第一版没有 provider 初始化或模型调用。
- 不执行仓库代码，不调用仓库 hook，不自动 fetch、pull、checkout、reset、clean、commit 或 push。
- 对本机仓库执行 Git 只读命令时限制超时与输出量；出错时把仓库保持原样并给出可读原因。
- 本地浏览器读取私有仓库元数据仍是敏感操作；不要在访问日志中写提交消息、文件列表或绝对路径。关闭服务后，进程内目录和缓存消失。
- 不读取、覆盖、移动或清理 ignored 实验证据；不重算 Rich/Click 冻结分析。

## 11. 性能与缓存

仓库列表只检查显式登记的路径。提交列表按 50 条分页，不在启动时对整个历史逐条评估；选中详情时才计算优先级。进程内缓存以规范化仓库 ID、完整 SHA、规则版本及 HEAD 锚为键；不写磁盘缓存。接口同时给出列表锚 SHA 与当前 HEAD SHA；二者不同则提示刷新并丢弃旧列表缓存，不把新提交混入旧分页。首次加载和切换仓库应立即显示加载状态，超时不显示半截结果。页面不承诺对百万提交仓库进行一次性全历史索引。

## 12. 异常和边界行为

| 情况 | 行为 |
|---|---|
| Git 未安装、目录不可读、不是工作树 | 启动前汇总全部失败路径并整体拒绝启动；不静默跳过其中一个仓库 |
| 已登记仓库后来被移动或删除 | 对该仓库显示不可用；其他仓库继续可看 |
| 仓库无提交 | 显示空历史，不生成风险标签 |
| detached HEAD | 显示 SHA 与 detached 状态，仍可浏览其可达历史 |
| 工作树未提交变更 | 显示 dirty 徽标，不改变历史提交评估 |
| 合并提交、二进制或不完整统计 | manual_review，列明原因 |
| HEAD 在浏览期间变化 | 旧页面保持同一锚；提示用户刷新以查看新历史 |
| Git 命令超时或输出过大 | 接口返回明确错误；不把截断数据当完整输入 |
| 文件名或标题含 HTML/控制字符 | 作为文本安全显示，不执行脚本，不污染日志 |
| 指向未登记仓库或非法 SHA 的请求 | 404/400，不回显本机路径 |

## 13. 测试与验收

### 13.1 纯逻辑测试

用临时 Git 仓库构造小改动、大改动、敏感路径、删除、重命名、根提交、合并、二进制、无提交和 dirty 工作树。风险规则必须覆盖四种输出、阈值边界、理由顺序、规则版本及缺失值。用恶意文件名/提交标题检验 JSON 与页面文本渲染。测试不读取真实 .env。

### 13.2 服务与界面测试

验证仓库 ID 隔离、分页游标绑定、HEAD 变更提示、非法 SHA、超时、移动仓库和只读方法限制。浏览器人工验收覆盖三栏、窄屏、键盘焦点、空/加载/错误状态；必要时增加自动化页面测试，但不为镜像实现写重复测试。

### 13.3 项目回归

使用 D:\envs\codeagent\Scripts\python.exe、显式 PYTHONPATH=src、每次独立 --basetemp 运行全项目 pytest；执行 Ruff、git diff --check、相关产物秘密格式扫描。两项既有 Windows symlink capability skip 如仍存在，单独报告。核对 Rich 三份冻结 SHA-256、最终比较文件及 Git 工作树状态；不以旧的 468 passed 数字替代新的验证结果。

### 13.4 用户验收路径

1. 从一个干净的本机环境启动工作台，传入两个预先准备的 Git 仓库。
2. 在左栏切换仓库，确认每个仓库的 HEAD 与历史不同。
3. 在中栏翻页并打开普通、敏感路径、合并三种提交。
4. 在右栏核对优先级、命中依据、manual_review 与信息缺口。
5. 关闭工作台，确认两个仓库的 Git 状态、引用及文件内容与启动前一致。

## 14. 分阶段实施与权限门

1. **设计审阅门（已通过）**：用户已确认本文件；逐任务实施计划仍需单独审阅。
2. **只读数据内核**：先实现登记、Git 读取、规范化和风险规则，配临时仓库测试。此步不做浏览器外观，不调用 provider。
3. **本地浏览器纵向切片**：静态页面、只读 API、三栏交互和错误状态。只读取显式仓库。
4. **文档与验收**：更新 README 中过时的阶段说明，写启动和演示说明，执行完整验证与安全检查。
5. **后续独立设计**：私有 GitHub 账户接入、Agent 修复、PR 回写、外网托管分别需要自己的权限、数据传输和验收设计；第一版本阶段完成不自动授权它们。

## 15. 未来扩展接口

### 15.1 私有 GitHub 来源

最终演示可只包含私有 GitHub 仓库。后续新增 GitHub 账户授权和最小只读权限，读取账户可访问的仓库、提交和可用检查结果；再规范化为本设计的 RepositorySummary、CommitSummary、CommitDetail。GitHub 数据需要显式区分远端检查结果与本地无检查数据。账户 token 不进入浏览器页面、URL、日志或报告。是否部署在本机或远端、如何处理私有源码和授权续期，必须在独立设计中确定。GitHub 来源不能悄悄改变 V1 审查规则；新增 CI 信号须升级规则版本。

### 15.2 Agent 维护流程

未来从提交或 Issue 手动创建维护任务时，读取来源仓库的固定 SHA，准备隔离工作空间，运行 Agent、公开验证、补丁捕获与人工审查。Agent 输出与 V1 历史提交优先级是两个独立对象；不能把审查优先级当成 Agent 任务成功率。任何新真实运行、provider 调用、回写本地仓库或创建 PR 都需要相应用户授权。旧 Rich/Click 正式槽位永不补跑。

## 16. 本阶段完成定义与非主张

以下全部满足，才可称本地核心完成：

1. 显式多仓库目录、提交历史、单提交详情和四类审查优先级可在浏览器中使用。
2. 判定依据可由规则版本和提交统计机械复算；manual_review 与缺失证据不会被隐藏。
3. 异常、路径、安全及多仓库隔离测试通过；来源工作树与 Git 引用未改变。
4. 真实全项目测试、Ruff、diff、安全扫描及冻结证据核验有本轮新鲜记录。

本阶段不声称发现真实漏洞、预测缺陷概率、提升 Agent 修复成功率、完成私有 GitHub 接入，或复现 Rich–Click 的方向性结果。其价值是建立可信的产品入口和可解释的提交审查层，为后续受控 Agent 维护流程铺路。
